# OpenEvidence Exhibit A — Gap Analysis

Source: `OpenEvidence_Customer_Proposed_Exhibit_A_Information_Security_Measures.docx` (customer-proposed replacement draft to Pilot Order Form dated 2026-04-27).

This doc splits every commitment in the exhibit into:

- **Cycloid — code** (engineering work in this repo / sandbox image / infra)
- **Cycloid — non-code** (policy, paperwork, contracts, audits, certifications, internal process)

Within each bucket, items are tiered:

- ✅ **Already do** — current behavior already satisfies (or substantially satisfies) the ask
- 🟢 **Minimal lift** — small, well-scoped change; days to ~2 weeks of work
- 🟡 **Heavy lift** — months of work, new subsystem, vendor coordination, or org-wide rollout
- 🔴 **Can't do (or commit not to)** — operationally or commercially infeasible as written; needs renegotiation

Section references map to the exhibit (`§<n>.<m>`).

### 🔴 Can't do as written (need counter language)

| §                     | Ask                                                                                                                                                                                                                                                          | Why / Counter                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| §5.2                  | Sandbox filesystems destroyed **immediately upon Session end, timeout, Customer revocation, or task completion** unless Customer affirmatively enables persistence. Paused/resumable sandboxes disabled by default for restricted repos.                     | Pause/resume is foundational to the Cycloid developer experience — the box has to come back when the developer comes back. "Destroy on timeout" forces either bad UX (developer can't resume) or unviable unit economics (holding idle sandboxes for days). **Counter:** destroy on actual session end / customer revocation / explicit Customer-set max age; pause/resume window is customer-configurable with a documented default; restricted repos can opt out of pause/resume.                                        |
| §5.5                  | "Provider shall not use Customer Content, repositories, Session state, transcripts, or artifacts for Provider product development, model training, model fine-tuning, benchmark creation, internal demos, sales, marketing, analytics, or unrelated testing" | We don't train or fine-tune on Customer Content. **But** our LLM observability service (Braintrust) ingests session data so we can debug, root-cause, and deliver SLA. Without it, time-to-fix on customer-reported issues balloons. **Counter:** carve out service-operation observability (debugging, monitoring, incident response, SLA enforcement) from the prohibition; training / fine-tuning / benchmarks / demos / sales / marketing / analytics remain prohibited.                                               |
| §8.5 (one piece only) | "Human approval before actions that modify source code, CI/CD, deployments, secrets, package publishing, access controls, or external systems"                                                                                                               | Background agents are valuable precisely because they can take a task end-to-end without per-step approval. The customer authorizes the work scope when they assign the task; agent runs within scoped tool policies, branch protections, and write-path restrictions (§4.6). Per-tool-call human approval defeats the product. **Counter:** customer authorization is granted at task assignment; agent's modifications are constrained by §4.6 write-path restrictions, branch protection (§15.2), and §4.7 attribution. |
| §3.3                  | Privileged Access disabled by default; named-user, JIT, time-limited, ticketed, **approved by Customer in writing each time** except for emergency access                                                                                                    | Customer pre-approval of every internal engineering privileged-access event is operationally impractical at our team size and incident cadence. **Counter:** named-user only, JIT, time-limited, ticketed, FIDO2/WebAuthn MFA, audit-logged, with 24h post-hoc notification + break-glass policy (§3.4 — kept). Eliminates the per-event written-approval requirement; preserves visibility and accountability.                                                                                                            |
| §1.3 / §4.3 / §13.3   | "30 days advance written notice before any material change to architecture, hosting, model providers, GitHub App permissions, Subprocessors, retention, logging, encryption, privileged access, or egress" / before adding/changing Subprocessor             | 30-day pre-notice on security control changes blocks security fixes and routine vendor swaps. We're moving fast and can't block on a 30-day window. **Counter:** prompt notice (e.g., 30 days for net-new Subprocessors with Customer Content access), **post-hoc** notice for security-driven changes, exception for emergency mitigations.                                                                                                                                                                               |
| §10.4                 | Vulnerability remediation SLAs (crit 7d / high 30d / medium 90d / actively exploited 72h) as a flat contractual commitment                                                                                                                                   | Want internally, but can't commit to flat windows for every finding regardless of context. **Counter:** "commercially reasonable efforts" with the same target tiers.                                                                                                                                                                                                                                                                                                                                                      |
| §1.2 / §2.1           | "Consistent with industry-standard security practices for SaaS services handling confidential source code, **PHI**, and **high-value intellectual property**" as a flat representation                                                                       | We're on board with this, but full execution depends on BAAs with all subprocessors (currently only OpenAI has one). **Counter:** PHI-specific obligations apply only when PHI handling is enabled for the business and the required subprocessor BAAs are in place.                                                                                                                                                                                                                                                       |

## Cross-cutting observations

1. **The §17 attachment package is the highest-leverage non-code work.** Architecture diagram, data-flow, subprocessor list, GitHub App manifest, data inventory, retention map, privileged-access policy, IR contact — bundling these unlocks most "minimal lift" non-code items without code changes.

2. **The heaviest _code_ workstream is now §9.4 retention.** With §6 confirmed already-do, §8.1/§8.4/§8.5 confirmed largely already-do, and §3.5 reframed as minimal lift, the remaining real engineering work is the retention windows + automated purge system.

3. **SOC 2 + initial pentest are bundled and contractually deferred.** SOC 2 audit kicks off June 2026, Type II ~4 months later, initial pentest commissioned as part of the audit cycle. We cannot gate signing or restricted-repo access on either being complete today; we propose an interim assurance package (§11.3 minimal-lift items) and product-level restricted-mode controls (§15.3) to bridge.

4. **PHI (§14) is gated on subprocessor BAAs.** OpenAI BAA done; AWS / Braintrust / E2B / Cloudflare BAAs in flight via §13.2 workstream. Can't commit to PHI handling end-to-end until those land.

5. **The operationally-spiky contractual asks** all flagged for redline with counter language: 30-day prior notice (§1.3/§4.3/§13.3), customer pre-approval for every privileged-access event (§3.3), immediate sandbox destruction (§5.2), no-internal-reuse with no observability carve-out (§5.5), per-tool-call human approval (§8.5), SOC 2 Type II as precondition (§11.3/§11.4), pre-restricted-repo pentest (§10.2), flat annual-pentest commitment (§10.3), unilateral "additional security evidence" lever (§11.4), terminate-without-penalty for foundational Subprocessor objections (§13.3), and the contra-proferentem clause (§18).
