# How to think through the sequencing of a project

This is a guide for how to scope and order your work.
Read it before you plan a V1.

## The main idea

Your **V1 should be the smallest thing that gives a real user real value.**
Not everything you can imagine. Just the first useful piece.

After V1 ships, you add the next smallest useful piece.
Then the next one. Small, useful, again and again.

## The trap to avoid

A common mistake looks like this:

> "For V1 I will build A, B, C, D, E, F, and G."

That is **not a V1.** That is a whole roadmap.

If you build all of it before shipping, the user gets value very late.
We want value **early**, then we grow it.

The reason is simple: we learn from real users, not from plans.
The faster a user touches the feature, the faster we learn what to build next.
A big V1 delays that learning for weeks. A small V1 starts it now.

## How to pick your V1

1. **Break your idea into small separate pieces.**
   A, B, C, D... treat each one on its own.
2. **For each piece ask:** "If we shipped only this, would a user get value?"
3. **Pick the one piece that gives the most value for the least work.**
   That is your V1. Ship it.

The test for a good V1:

> "If we shipped only this and nothing else, would a real user get real value?"

- **No** -> it is not a V1. It is a fragment. Cut more.
- **Yes, but only a little** -> that is your V1. Ship it.
- **Yes, and it does 5 things** -> you bundled many versions together. Split them.

## How to pick what comes next

After V1 ships, ask:

> "What is the next smallest thing that adds the most value?"

Build that. That is V2.
Then repeat the question for V3, V4, and so on.

Re-ask this **after each version ships**, not all at once at the start.
Real usage changes the answer. What looked important in the plan may not matter,
and something you did not expect may become the most valuable next step.

## The one thing to remember

Every version = the next smallest step that gives real value.

Small, useful, again and again.
