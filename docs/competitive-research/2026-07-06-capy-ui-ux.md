# Capy UI/UX teardown

Observed July 6, 2026 from the authenticated Capy app on project `excalidraw`.

## Cycloid baseline

Cycloid is organized around a flat session list plus a centered task composer. The top-level app has no project marketplace, no PR inbox, no role-specific context management page, and no IDE-like tab system. Product configuration lives under Settings.

Capy is organized around a project workspace called `Captain threads`. It feels less like "submit a background job" and more like an IDE/team cockpit for many agent threads inside one repository/project.

## Information architecture

Capy's top-level nav in the project:

- Dashboard
- Threads
- PRs
- Automations
- Explore
- Context
- Folders
- Recents
- Settings

The biggest difference from Cycloid is that Capy separates:

- thread management
- PR review/triage
- automation templates
- context/instructions
- marketplace/templates
- project/user/org settings

Cycloid compresses most of this into:

- Home composer
- Session list
- Session detail
- Settings

Capy makes the project itself the durable container. Cycloid makes the session the durable container.

## Dashboard / thread cockpit

Observed dashboard:

- Project switcher at top (`excalidraw`).
- Search with `cmd` hint.
- Main nav and recents in left sidebar.
- Central title: `Captain threads`.
- Tab-like `Dashboard` control.
- `New tab` button.
- Central composer: `Ask Captain Capy...`
- Add context button.
- Model selector: `GPT-5.5`.
- Voice input button.
- Branch selector: `master`.
- File/image upload inputs.
- Suggested prompt chips:
  - Summarize latest changes
  - Review my latest PR
  - Suggest a new feature...
  - Create a task for...
- Participant filter chip (`Shivam Pandey`).
- Thread search input.
- Sort and filter buttons.
- Status grouping (`Idle`).
- Thread row with task key (`EXCAL-001`), title, model, age, PR number.
- Support chat widget.

Cycloid home is cleaner but less operational. It asks "what should Cycloid build?" and starts a session. Capy's dashboard already assumes a world of ongoing agent threads and gives controls for filtering, participants, status, branches, suggestions, and tabs.

## Thread and folder model

Capy exposes Folders and Recents in the sidebar. The active project showed:

- Folder controls
- Create folder
- Recents group
- Pin/archive/thread options on recent thread rows

Cycloid has session list filtering/archive, but not user-defined folders or a project-local thread organization model. This matters because Capy can support many parallel threads inside a repo without forcing everything into chronological history.

## PR inbox

Capy's PR page is top-level and structured as a PR workflow:

- New
- Open
- Pinned
- Approved
- Needs review
- Draft
- Closed
- Fetch older pull requests

Observed rows included:

- PR number
- title
- base branch
- head branch
- model/thread metadata (`GPT-5.5`, `EXCAL-001`)
- updated age
- additions/deletions

This is a major IA difference. Cycloid surfaces PR state inside each session, and its sidebar can show PR-ready sessions, but it does not provide a PR inbox as a first-class page. Capy treats PRs as an organizing object parallel to threads.

## Automations

Capy automations are top-level. Observed empty state and templates:

- `New` automation CTA.
- "Set up recurring tasks - Capy runs them on schedule and reports back."
- Popular templates:
  - Find critical bugs
  - Summarize changes daily
  - Crash triage
  - Security review
  - Dependency health
  - Stale PR cleanup

Cycloid's automations live under Settings and currently focus on scheduled runs plus Slack alert automation from Datadog/Sentry. Capy makes automations discoverable and opinionated with product-language templates.

## Context page

Capy's Context page is unusually direct and useful. It manages instruction files:

- `CLAUDE.md`: fallback when `AGENTS.md` is absent, overridden by role-specific `.capy` files.
- `AGENTS.md`: default instructions overridden by role-specific `.capy` files.
- `capy/BUILD.md`: build instructions that override default instructions.
- `capy/REVIEW.md`: review instructions that override default instructions.
- `capy/CAPTAIN.md`: Captain instructions that override default instructions.

It also shows:

- installed skills
- edit skills
- browse skills

Cycloid has repo instructions and skills, but we do not expose instruction precedence as a UI. Capy's UX teaches users the hierarchy and maps instructions to agent roles. That is especially strong for trust: users can see exactly why Build/Review/Captain agents behave differently.

## Explore marketplace

Capy's Explore page is a marketplace:

- Search project starters, automations, and skills.
- Tabs:
  - Projects
  - Automations
  - Skills
  - Org templates
  - My templates
- Author filter.
- Sort by popularity.
- `Add your own template`.
- Template cards with:
  - verified badge
  - description
  - popularity/star counts
  - author
  - `Use template`

Observed project templates included Vercel AI Chatbot, Next.js SaaS Starter, Next.js Boilerplate, Tailwind blog starter, Morphic, SaaS Boilerplate, next-forge, dashboard starters, ecommerce starters, Supabase/OpenAI doc search, and more.

Cycloid has no marketplace or starter/template browsing surface. We rely on the user bringing a repo/task. Capy can start from "what do I want to create?" rather than "which existing repo should the agent modify?"

## Features Capy has that Cycloid does not

- Project-level dashboard with threads, PRs, automations, context, and marketplace as first-class nav.
- Thread folders.
- Project-local tabs/new-tab behavior.
- Participant filters for thread lists.
- Voice input in the composer.
- Branch selector in the composer.
- Suggested prompt chips on the dashboard.
- PR inbox with review-state buckets.
- PR rows linked back to thread IDs and model metadata.
- Recurring automation template gallery.
- Crash triage automation template.
- Dependency health automation template.
- Stale PR cleanup automation template.
- Instruction-file precedence UI.
- Role-specific instruction files: Build, Review, Captain.
- Skills marketplace/browse flow.
- Project starter marketplace.
- Org and personal templates.
- In-app tab preference vs browser tabs.
- Default diff view and diff color preferences.
- Pull request author override in user preferences.
- Capy-managed GPG commit signing.
- Auto-react-to-CI preference.
- Auto-react-to-merge preference.
- Auto-react-to-merge-conflict preference.
- Merge conflict auto-handling age limit.
- Personality/tone control across web, Slack, and Linear.
- Project-scoped environment variables page.
- Project-scoped MCP servers page.
- Activity and audit log as org settings.
- Service users as org settings.

## Features Cycloid has that Capy did not clearly show

- Cycloid's repo docs strongly enforce control-plane-owned auth/authorization/credential resolution.
- PR-as-user is a core Cycloid contract; Capy's PR author setting exists, but exact security posture was not verified in this inspection.
- Cycloid has explicit Jira support in repo docs; Capy's observed settings mentioned Slack/Linear in personality copy, but Jira was not visible.
- Cycloid has QA verification child-session concepts and FSM-backed PR lifecycle state; Capy has PR management/reactions, but not the same visible verification-state machinery.

## Product takeaways

Capy's strongest UI lesson is role and project organization. It makes "what kind of agent work is this?" concrete:

- Captain threads
- Build instructions
- Review instructions
- Captain instructions
- PR inbox
- Context page

Cycloid should consider making repo context/instructions and PR review status more visible outside Settings/session detail. Capy's `Context` page is especially worth copying in spirit: users should not need to read `AGENTS.md` docs to understand what instructions are active.
