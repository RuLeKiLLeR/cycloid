# Reconcile Cycloid Memory PRs

Takes no arguments. Work in the current repository.

## Goal

Process every open Cycloid-generated memory PR and choose exactly one outcome per PR:

- merge it
- close it as not worth applying
- leave it open only when blocked by merge state, failed checks, missing access, or genuinely ambiguous evidence

Report a score and rationale for every PR. Act only on memory PRs generated by Cycloid.

## Step 1: Reconfirm The Memory PR Shape

Before acting, inspect the current code that creates memory PRs:

```bash
rg -n "MEMORY_BRANCH_PREFIX|buildPrTitle|buildPrBody|Memory update from review|Merge to apply|memoryPathForFile|parseMemoryFile" \
  apps/control-plane-worker/src shared/memory tests
```

Expected current signals:

- branch prefix: `memory/update-from-pr-`
- author: the Cycloid GitHub App bot. The login differs by API surface: the REST `pulls` endpoint (Step 2) reports `.user.login` as `cycloid[bot]`, while `gh pr view --json author` reports `.author.login` as `app/cycloid`. Match whichever value the command you are running actually returns.
- title prefix: `[ARC] Memory update from review of PR #...`, `[ARC] Memory & convention updates from review of PR #...`, or `[ARC] Convention updates from review of PR #...`
- body starts with `## Memory updates from [PR #...]` and ends with `Merge to apply. Close to discard.`
- memory file changes live under `.cycloid/memory/**/*.md`
- convention updates, if present, target the allowed docs listed in `apps/control-plane-worker/src/constants/memory.ts`

If the code has drifted, adapt candidate detection to the code, not stale assumptions.

## Step 2: Discover Candidate PRs

Derive the repo from the checkout, list every open PR (paginated), filter to PRs authored by Cycloid. The REST `pulls` endpoint reports the bot as `cycloid[bot]` (NOT `app/cycloid`, which is only what `gh pr view --json author` returns), so the `--jq` filter must match `cycloid[bot]`:

```bash
gh api --method GET --paginate repos/{owner}/{repo}/pulls -f state=open -f per_page=100 \
  --jq '.[] | select(.user.login == "cycloid[bot]") | {
    number,
    title,
    body,
    author: { login: .user.login },
    headRefName: .head.ref,
    baseRefName: .base.ref,
    isDraft: .draft,
    mergeStateStatus: .mergeable_state,
    url: .html_url,
    updatedAt: .updated_at
  }'
```

If that returns nothing, do not assume there are no memory PRs: list every open PR with its `.user.login` (`gh api ... --jq '.[] | {number, author: .user.login, headRefName: .head.ref}'`) and confirm the bot login has not drifted again before concluding the sweep is empty.

Keep only PRs where all of these hold:

- `author.login` is `cycloid[bot]` (REST) / `app/cycloid` (via `gh pr view --json author`)
- `headRefName` starts with `memory/update-from-pr-`
- `baseRefName` is the default branch, usually `main`
- the title/body matches the memory PR shape from Step 1

For each candidate, fetch metadata and diff:

```bash
gh pr view <N> --json number,title,body,author,headRefName,baseRefName,isDraft,mergeStateStatus,url,files,commits
gh pr diff <N>
```

Continue automatically only if changed files are limited to:

- `.cycloid/memory/**/*.md`
- allowed convention docs from `CONVENTION_TARGET_FILES`

If a candidate edits code, migrations, workflows, infra, or unrelated docs, leave it open and report the scope mismatch.

## Step 3: Parse The Proposed Changes

For each memory file in the diff:

1. Read the full proposed file from the PR head:

```bash
gh api --method GET repos/{owner}/{repo}/contents/<path> -f ref=<headRefName> --jq '.content' | base64 --decode
```

2. Validate it against the current Memory 2.0 parser when practical:

```bash
npx tsx -e "import { readFileSync } from 'node:fs'; import { parseMemoryFile } from './shared/memory/parser.ts'; const p=process.argv[1]; const m=parseMemoryFile(readFileSync(p,'utf8')); if(!m){process.exit(1)} console.log(JSON.stringify({id:m.id,status:m.status,context_hint:m.context_hint,content:m.content}, null, 2));" <local-file>
```

3. Extract:

- `context_hint`
- `content`
- `applies_to`
- `source_pr_urls`
- `source_session_ids`
- semantic fields: `memory_type`, `action_type`, `level`, `primitive`, `engineering_domains`, `confidence`, `authority`, `enforcement`, `triggers`

For convention doc changes, extract the exact added text and target section.

## Step 4: Gather Evidence

Use authenticated local GitHub CLI for private repo context:

```bash
gh pr view <source-pr> --json number,title,body,files,mergedAt,url
gh pr diff <source-pr>
```

Read the referenced files on current `origin/main`:

```bash
git fetch origin main
git show origin/main:<path>
```

Search existing memories and docs for duplicates or conflicts:

```bash
rg -n "<distinct terms from proposed memory>" .cycloid/memory docs AGENTS.md CLAUDE.md
```

If the memory cites session IDs and local tooling or app access can retrieve them, inspect the relevant transcript or evaluation evidence. Do not require session lookup when the source PR, review body, and code are enough to judge the memory.

## Step 5: Evaluate And Score

Score each proposed memory 1-5 for merge worthiness:

- `5`: Strong merge. High-confidence, non-obvious, broadly reusable, actionable next-time guidance with clear evidence.
- `4`: Merge. Useful, actionable, and not duplicated; minor wording or metadata imperfections acceptable.
- `3`: Borderline. Some signal, but too narrow, weakly evidenced, partially duplicated, or poorly framed. Prefer close unless there is a clear reason it will help future agents.
- `2`: Close. Mostly obvious, generic, too file-specific, stale, redundant, or weakly actionable.
- `1`: Close. Wrong, harmful, misleading, contradicted by current code/docs, invalid memory metadata, or likely to degrade future sessions.

Apply the analyzer's strong filter:

- Would a competent engineer still miss this after reading the relevant source?
- Does it apply to a recurring pattern, not one tiny historical incident?
- Is it not already captured in existing memories or docs?
- Is it surprising or codebase-specific rather than generic engineering advice?
- Does it say what to do next time, not merely what happened?

Close reasons:

- duplicates existing memory or convention docs
- restates visible code behavior
- only applies to a single exact bug with no reusable pattern
- generic advice such as "add tests" or "validate inputs"
- stale because the referenced code or workflow changed
- overly broad enforcement, triggers, or path globs that would annoy future sessions
- invalid Memory 2.0 frontmatter or semantic mismatch
- convention doc text too verbose for always-loaded instructions

Merge reasons:

- captures a reviewer/user correction not obvious from code
- prevents a repeated failure mode
- has clear source PR evidence
- is scoped to realistic triggers and referenced files
- is concise enough for retrieval without adding noise

## Step 6: Merge Or Close

For score `4` or `5`, merge if the PR is ready:

```bash
gh pr view <N> --json isDraft,mergeStateStatus,title,url
gh pr checks <N>
gh pr merge <N> --squash --delete-branch
```

If required checks are pending and GitHub allows auto-merge:

```bash
gh pr merge <N> --auto --squash --delete-branch
```

For score `1`, `2`, or normally `3`, close with a concrete comment:

```bash
gh pr close <N> --delete-branch --comment "<score>/5: <specific reason tied to the proposed memory and current code/docs>"
```

Do not edit the PR branch to improve a memory. The task is reconciliation, not repair.

Leave open only when blocked or ambiguous. If the user explicitly asked for every memory PR to be merged or closed, make a best-effort decision unless acting would be unsafe or impossible.

See [the shared Skill Feedback Loop guidance](docs/skill-shared.md#skill-feedback-loop).

## Step 7: Report The Sweep

Concise summary with these sections when applicable:

### Merged

- PR number and title
- score
- one sentence on why the memory was worth applying

### Closed

- PR number and title
- score
- one sentence on why it was not worth applying

### Left Open

- PR number and title
- exact blocker or ambiguity

### Skill gaps

- Friction events and proposed fixes per the Skill Feedback Loop section; omit when there was none.

## Rules

- Use current code to define memory PR detection before sweeping.
- Fail closed on memory quality: bad memories are worse than no memories.
- Do not touch non-Cycloid PRs or non-memory PRs.
- Do not merge draft PRs, conflicted PRs, or PRs with failed required checks.
- Do not close solely because checks are pending; score the memory first, then either auto-merge if allowed or report the blocker.
- Keep close comments specific enough that a human can see what failed the memory filter.
